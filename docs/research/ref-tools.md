## Decisões respondidas

**1. anti-slop — Oxlint como portão viável?**
[verificado: github.com/dmmulroy/anti-slop, README, 2026-09-10] É um plugin Oxlint (`jsPlugins`) vendorizado, não um pacote npm fixo — instala-se copiando `src/` para o repo alvo e registrando em `oxlint.config.ts`. Cobre só TS/JS (Effect como grupo opt-in separado). [inferido] Falsos positivos são prováveis porque o autor descreve as regras como preferência pessoal ("reflects my preferences and taste"), não padrão consensual — ex. `no-array-filter-map` rejeita passes eager adjacentes mas pode capturar composições legítimas de pequena escala. [verificado: WebSearch 2026-09-16] Existem concorrentes mais novos e menos opinativos: `antfu/eslint-plugin-slop` (7 regras, v0.1.2), `eslint-plugin-ai-guard` (17 regras, presets recommended/strict/security), `jantimon/eslint-plugin-no-comment-slop` (roda em ESLint, oxlint e rslint pela API de regra comum). Não há equivalente para Python/Go/Rust encontrado na busca — a categoria "anti-slop lint" é hoje exclusiva do ecossistema JS/TS. Para a ADE (multi-linguagem), a decisão é usar Oxlint+um destes plugins como *um* dos gates de lint quando o projeto gerado é TS/JS, mas não terceirizar a definição de "slop" nele — a ADE precisa de heurísticas próprias (ou reuso de regras estáticas de linter nativo) por linguagem, já que não existe equivalente pronto para Python/Go/Rust.

**2. open-code-review — "revisão híbrida" e chave de API**
[verificado: README + docs oficiais] "Hybrid deterministic+LLM" = pipeline de regras estáticas embutidas (NPE, thread-safety, XSS, SQL injection, multi-linguagem) que filtram candidatos, mais um agente LLM com tool-use que lê o diff, abre arquivos completos, busca no código e escreve comentários line-level — não é RAG simples, é um agente com ferramentas rodando sobre o diff. Benchmark próprio (AACR-Bench, HuggingFace, 200 PRs reais, 1505 issues anotadas por 80+ engenheiros) mostra maior precisão/F1 que agentes genéricos usando ~1/9 dos tokens, à custa de recall menor (trade-off deliberado por precisão). [verificado] Requer configurar um provider LLM (`ocr config provider`) com chave própria *exceto* em Delegation Mode (`ocr delegate`), onde o próprio agente hospedeiro (Claude Code, Codex, Cursor) executa a revisão e o OCR só resolve seleção de arquivo e regras — isso não conflita com "tudo via CLI/agente já autenticado". Vale como **Checker pré-merge opcional** via Delegation Mode; como serviço autônomo com LLM próprio, é um provedor extra a gerenciar e rejeitamos essa via para a ADE.

**3. reticle — percepção de runtime além de screenshot**
[verificado: README, tabela comparativa] Captura corpo de resposta de rede amarrado ao clique (`net`), estado real da store da aplicação (não o número renderizado), sinais customizados emitidos pelo app, stream de console, e commits do React fiber — nenhum desses chega a um screenshot ou é lido por Playwright/DevTools MCP (que só veem DOM + CDP cru, sem estado de aplicação nem `file:line` de origem). Retorna veredito pass/fail/"couldn't tell" com evidência estruturada e a localização no código-fonte, não pixels. [inferido] Maturidade: repositório com 663 stars, última atividade relevante 2026-09-11, produto ainda de único vendor comercial (reticle.sh), licença Apache-2.0 SDK + FSL para o resto (Functional Source License — não é OSI-approved até a data de conversão). Não serve para o runtime de referência da ADE hoje (Python/CLI, sem DOM), mas o *padrão* de asserção composta com evidência e `file:line` é diretamente reaproveitável no design do Checker para quando a ADE gerar apps web.

**4. caliper — protocolo de A/B para harness doctor**
[verificado: README] Métrica: taxa de sucesso por task (`expect:` julgado por LLM juiz, `assert:` determinístico em Python, `activates:` verifica se a skill certa disparou), agregada em `pass@k`/`pass^k` sobre k repetições. Protocolo de comparação pareada: `caliper run spec.eval.yaml --k 3` roda a task set com a skill presente; `--ablate <skill>` roda a mesma task set sem ela; `caliper compare run1.json run2.json` faz diff task-a-task de sucesso, tokens e wall-clock. Isso é exatamente o desenho que o harness doctor da ADE precisa para responder "esta regra/skill/portão realmente ajuda, e quanto custa": mesma task set, controle com e sem o candidato, diff pareado, e uma métrica de ativação separada da métrica de acerto (evita confundir "a regra carregou" com "a regra funcionou"). Reaproveitável como protocolo mesmo sem adotar o pacote Python `caliper-eval`.

**5. ouroboros e Chisle — uma ideia cada**
- Ouroboros: gate de ambiguidade numérico pré-código (entrevista socrática → score ≤ 0.2 bloqueia geração sem `force` explícito). Vale registrar como padrão de portão de intenção antes do primeiro artefato de código; o resto ("Agent OS", 14 runtimes, "evolutionary loop") é retórica de produto sem evidência adicional — **REJECT**.
- Chisle: hook pós-ferramenta que faz scrub/elide/dedup na saída bruta antes de reentrar no contexto (eixo de entrada, separado do eixo de prosa/código), com a disciplina de publicar o pior caso do próprio benchmark (não só a média) — método de honestidade de benchmark reaproveitável para qualquer claim de economia de token na ADE. O restante (persona terse redundante com convenções já em uso) — **REJECT**.

## Busca por alternativas melhores (curta)

- **Lint anti-slop para agentes** [verificado: WebSearch 2026-09-16]: `antfu/eslint-plugin-slop`, `eslint-plugin-ai-guard` (presets), `jantimon/eslint-plugin-no-comment-slop` (multi-linter: ESLint/oxlint/rslint). Todos ainda TS/JS-only; nenhuma alternativa para Python/Go/Rust encontrada.
- **Code review por agente open source** [verificado: WebSearch]: PR-Agent (Qodo, ~8.5k stars, self-hosted com chave própria), Qodo Merge (open-core, multi-plataforma Git), Kodus AI, Shippie/code-review-gpt (MIT, CI-first). Todos exigem chave de LLM própria como o OCR em modo autônomo — nenhum resolve o problema de "sem chave extra" melhor que o Delegation Mode do OCR.
- **Percepção de runtime** [verificado: WebSearch]: Chrome DevTools MCP (Google, exposição de DevTools via MCP — mais próximo de Playwright que de Reticle, sem estado de app), Vercel `agent-browser` (primitivo de controle bruto, sem asserção estruturada), Frontman/Tidewave (mencionados só em conteúdo de terceiros, não verificados em fonte primária — tratar como hipótese). Nenhum expõe estado de store + assert composto com `file:line` como o Reticle; a lacuna que o Reticle preenche segue sem alternativa madura equivalente.
- **A/B de harness/skills** [verificado: WebSearch]: `bobmatnyc/ai-harness-benchmark` (mede tokens/custo/qualidade/velocidade entre harnesses, não entre skills dentro do mesmo harness — escopo diferente do caliper). Nenhuma alternativa encontrada que replique o protocolo de ablação pareada por task do caliper especificamente para skills.
